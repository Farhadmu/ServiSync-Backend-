# ServiSync — Phase 1: Architecture & Database Design

## Project Overview

**ServiSync** is a centralized Field Service Management System backend.
The system digitizes the complete service lifecycle: customers request services, managers review and assign technicians, technicians perform field work and submit reports, administrators manage users/payments/analytics, and all roles interact through role-enforced REST APIs.

- **Project**: ServiSync
- **Category**: Business / Operations — Field Service Management
- **Stack**: Node.js + TypeScript + Express + PostgreSQL + Prisma + Zod + JWT + bcrypt + Redis + Cloudinary + Stripe
- **API Versioning**: `/api/v1/...`

## Status Ownership & State Transitions

To avoid duplicate state ownership, each model owns its own lifecycle:

### ServiceRequest (high-level request lifecycle)
`PENDING → UNDER_REVIEW → APPROVED | REJECTED | CANCELLED → CLOSED`

- Created by Customer → `PENDING`
- Manager reviews → `UNDER_REVIEW`
- Manager approves → `APPROVED`; rejects → `REJECTED`
- Customer/Manager cancels (in allowed states) → `CANCELLED`
- After payment success → `CLOSED`

### Assignment (assignment & scheduling lifecycle)
`PENDING → SCHEDULED → ACCEPTED | REJECTED | CANCELLED`

- Manager assigns → `PENDING`
- Manager schedules → `SCHEDULED`
- Technician accepts → `ACCEPTED`; rejects → `REJECTED`
- Cancelled before acceptance → `CANCELLED`

### WorkOrder (field execution lifecycle)
`SCHEDULED → ARRIVED → IN_PROGRESS → COMPLETED | CANCELLED`

- Created from ACCEPTED assignment → `SCHEDULED`
- Technician marks arrival → `ARRIVED`
- Starts work → `IN_PROGRESS`
- Marks complete → `COMPLETED`
- Cancelled → `CANCELLED`

### Invoice (financial lifecycle)
`DRAFT → PENDING → PAID | PARTIALLY_PAID | VOID`

- Generated by Manager after `COMPLETED` → `PENDING`
- Payment verified → `PAID`
- Manager voids → `VOID`

### Payment (gateway lifecycle)
`PENDING → PROCESSING → SUCCESS | FAILED | CANCELLED | REFUNDED`

- Customer initiates checkout → `PENDING`
- Gateway processes → `PROCESSING`
- Gateway verifies success → `SUCCESS` (ONLY via verified callback/webhook)
- Gateway fail/cancel → `FAILED` / `CANCELLED`

### Feedback
Eligibility: `WorkOrder.COMPLETED` AND `Invoice.PAID` (i.e., service fully closed). Customer submits rating (1–5) + comment.

### Polymorphic Attachment Design

Because Prisma does not support polymorphic relations natively, `Attachment` uses scalars:
- `entityType` (AttachmentEntityType enum)
- `entityId` (String)

The service layer fetches attachments with `WHERE entityType = ? AND entityId = ?`.
No Prisma relation fields are declared on `ServiceRequest`, `WorkOrder`, or `ServiceReport` to avoid invalid schema.
File metadata (url, publicId, filename, mimeType, size, width, height, purpose) is stored on `Attachment`.
`purpose` enum allows distinguishing `BEFORE`, `AFTER`, or `GENERAL` images for a given entity.

## Technician Assignment Logic (Phase 5 Implementation Contract)

1. Verify `ServiceRequest` exists and is in an assignable state (`APPROVED`).
2. Verify `TechnicianProfile` exists and `isActive=true`.
3. Verify technician has all `requiredSkills` for the `ServiceType`.
4. Verify technician is available (`TechnicianProfile.isAvailable=true`).
5. Verify the requested schedule does not conflict with an existing active assignment for the technician.
   - Conflict formula: `newStart < existingEnd AND newEnd > existingStart`
   - Exclude assignments with status `CANCELLED` or `REJECTED`.
6. Create `Assignment` + schedule in a Prisma transaction.
7. Update `ServiceRequest.status` to a post-assignment state.
8. Create `AuditLog` and `Notification`.

Race-condition protection:
- Use a Prisma transaction with `serializable` isolation (Postgres default `READ COMMITTED`; wrap critical section with `SELECT ... FOR UPDATE` if needed).
- Re-verify technician availability/conflicts inside the transaction before insert.

## Security Considerations

- `bcrypt` password hashing (salt rounds configurable).
- JWT `access_token` (short-lived, 15m) + `refresh_token` (longer-lived, stored hashed in DB).
- `express-rate-limit` on auth endpoints.
- `helmet` for security headers.
- CORS with allowed origins.
- Zod validation on all inputs.
- No password hashes, refresh tokens, or secrets in API responses.
- Payment success ONLY via verified Stripe webhook/callback — never from client-supplied status body.
- Cloudinary URL validation + file size/type restrictions.
